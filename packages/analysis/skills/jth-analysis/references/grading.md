# 证据评审

使用 prepare 生成的判断模板，保留 `schemaVersion`、`bundleHash` 和 `rubricVersion`。填写实际 judge 的 model、分析会话 ID 和评审时间；无法取得 model 或会话 ID 时用 `null`，不猜测。

## 任务与适用要求

为所选的每个实际任务绑定来源会话，并按证据标记 `completed`、`in_progress` 或 `unknown`。依据当时生效的用户要求和规则；用户后续明确修订要求时记录其有效范围，普通补充不能悄悄替换原目标。不要用今天的新规则追溯扣罚旧执行。

先从完整原文及当时有效规则提取每个任务的 `requirements`，每条包含稳定 id、domain、text 和 sourceRefs。清单包括原目标、必需交付、授权范围、约束及本次适用的 Memo 要求；用户补充或修订须保留来源与有效范围。不可从已有评项、计划步骤或成功产物倒推清单，以免漏掉未完成要求。

把要求写成可分别判断的 criterion。每个评项的 `requirementIds` 对应同一任务、同一 domain 的实际要求；`requirementRefs` 指向支持判定标准的原文，`evidenceRefs` 指向实际执行或结果。所有引用使用 bundle 中真实 evidence ID；quote 必须是对应原文的连续子串。引文存在只证明来源存在，仍需判断它是否支持结论。

完成逐项判断后，再对照完整原文核对清单本身是否遗漏，填写任务的 `coverageReview`：status 为 `complete`、`incomplete` 或 `unknown`，reason 描述核对结果，evidenceRefs 引用核对依据。只有实际核对清单完整且所有有效要求得到明确判断，才允许正式总分。未核对或看不到完整来源用 unknown；已知漏项用 incomplete，并补充清单和评项后重新核对。

报告中的“已提交评项覆盖”只描述已提交 items，不能冒充“原始要求覆盖”。四个维度都有 items、当前评项全部通过、没有在结果中看到失败，都不能单独支持 100% 需求覆盖或正式满分。

## Flow 维度

| dimension | 权重 | 判断内容 |
|---|---|---|
| `goal_preservation` | 40% | 是否保留原目标；补充、恢复和阶段转换是否仍服务于有效目标。 |
| `deliverable_completion` | 30% | 用户要求的交付是否实现；阶段成果和最终完成是否区分。 |
| `scope_constraints` | 20% | 行动是否符合授权范围、有效约束和当时适用规则。 |
| `completion_evidence` | 10% | 完成结论是否对应实际产物或行为；失败、未执行和无法确认是否如实保留。 |

步骤多少、是否读取 Skill、是否输出进入回执，本身不是质量分。机器检查、提交或 Hook 成功不能单独证明完整需求达成。

## Memo 维度

| dimension | 权重 | 判断内容 |
|---|---|---|
| `memory_capture` | 30% | 明确决定和应复用信息是否被正确处理；Agent 决策与后续声明、接收、入库、索引是否对应。 |
| `memory_fidelity` | 30% | 内容和修订是否受真实来源支持，是否保留重要条件和纠正，是否把提案当决定。 |
| `scope_confirmation` | 20% | 范围、依据类别和确认程度是否对应来源，临时约束是否被误升为长期规则。 |
| `retrieval_application` | 20% | 查询、候选、读取和实际采用是否服务于当时问题，是否保留版本、时效和未知，是否把历史资料当当前指令。 |

入库回执、索引完成和读取版本是机械事实；匹配分、读取次数和 Agent 的 `used` 声明不能当作正确性或助力分。没有明确 record/skip 决定时，原因是未知；可以指出疑似遗漏，不能替 Agent 补造理由。

## 判定与严重程度

| status | 含义 |
|---|---|
| `satisfied` | 有证据支持满足要求。 |
| `partial` | 证据支持部分满足，并明确剩余条件。 |
| `violated` | 有证据证明违反要求。 |
| `unknown` | 证据缺失、任务边界不明或不能确认；填写 `missing`。 |
| `not_applicable` | 此项对该任务不适用，说明依据。 |

reason 指出具体来源、差异或缺失；不因文字自信、JSON 合法或真实 ID 就判通过。未执行检查不能标通过，judge 调用失败也不能当作任务的语义失败。

`severity` 使用 `normal`、`serious` 或 `critical`，依据违反要求的实际影响。关键约束违反或重大虚假完成单独列为 `critical`，不能被其他高分抵消；缺少证据本身不能冒充已观察到严重错误。

CLI 对 `satisfied`、`partial`、`violated` 分别使用 1、0.5、0 计算维度分，再按上述权重合计。不适用项需要证据与理由，排除后对适用权重归一；未知项、缺失维度、未完成的要求清单核对或未评有效要求保留证据缺口，不能给完整总分。只有已完成任务进入最终批次分；未完成任务显示阶段分，边界未知时不给最终分。不要为了获得总分删掉未知项或挑选成功记录。

## 可观察贡献

`contributions` 区分 `observed_help`、`observed_burden` 和 `no_effect_evidence`，并绑定实际 evidenceRefs。指出例如原目标在恢复后继续生效、计划约束促成纠偏、已读记忆改变了产物，或流程造成重复工作；只出现规则、回执或读取记录还不足以证明影响。

没有贡献证据时如实说明，不补写“如果没有 Workflow/Memo 就会失败”。报告评日常执行与可观察贡献，不声称已证明因果增益，也不为了评分额外跑任务或 A/B 测试。
