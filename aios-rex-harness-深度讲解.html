导读：30 秒版本

如果只看这一节，请看这里。

一句话：这两个仓库合起来，是给 AI 编码助手（Codex、Claude Code、Gemini CLI、OpenCode 等）装的一套"外挂大脑"——让你的 AI 记得住事（记忆）、按规矩干活（流程）、拿证据说话（验证），而且全部运行在你自己的电脑上，数据不出门。

🏠 AIOS —— 宿主 / 总管（外层大房子）

  • 是什么：一个本地优先的 AI 编码编排系统（约 15 万行 JS/TS）。
  • 管什么：项目记忆（ContextDB）、任务路由（Workflow Policy）、多 Agent 并行（team）、可恢复长任务（harness）、安全隐私门（privacy guard）。
  • 类比：一家公司的"总部"——有档案室、有调度台、有保安，但真正按工序生产零件的"核心车间"不是它自己造的。

⚙️ rex-harness —— 内核 / 工序引擎（核心车间）

  • 是什么：一个可独立运行的"软件工程控制面"（约 58 个源码文件的纯函数内核）。
  • 管什么：把任何开发任务拆成"观察 → 事实 → 能力 → 工单 → 证据"的循环，一次只发一张工单，干完必须交证据，证据不合格就阻塞。
  • 类比：工厂里铁面无私的"工序卡 + 质检员"——AI 想跳步？不行。想口头汇报"我做完了"？拿测试回执来。
两者的关系（一句话） rex-harness 以 git submodule（子模块） 的形式内嵌在 AIOS 仓库里（.gitmodules 中登记的唯一子模块），是 AIOS 声明的"必需规划内核"；AIOS 通过直接调用它的 JS API 来复用整套工作流状态机，并在外面补上记忆、执行、安全、协作这些"水电煤"。rex 单独也能用（独立模式），接上 AIOS 后获得全部宿主增强。

小白篇：这两个东西到底是干嘛的

不涉及任何代码细节，先把"人话版"讲明白。

1.1 先说痛点：现在的 AI 编码助手有三大毛病

你可能用过 Codex、Claude Code 这类"终端里的 AI 程序员"。它们很聪明，但有三个老大难问题（aios 文档站里专门有一篇 why-agents-forget-context.md 讲这个）：

毛病具体表现后果
😵 失忆 每开一个新会话，AI 把上周聊过的决策、改过的文件、踩过的坑全部忘光。 你不得不反复解释背景；AI 重复犯错、重复提问。
🃏 瞎干 你说"重构认证模块"，它一口气改十几个文件，跳过测试、跳过设计，一步到底。 改动太大没法审查；出问题不知道是哪一步引入的。
🤥 不自证 它说"修复完成、测试通过"，但你不知道它到底跑没跑测试——它可能只是"觉得"应该能过。 口头承诺不可信，最终还得你自己验证一遍。

1.2 AIOS：给 AI 装的"三件套外挂"

AIOS 的 slogan 是"一句话，搞定任何复杂任务"。它的思路不是再造一个 AI 客户端让你换掉，而是垫在你现有客户端下面补能力。装好之后（一条安装脚本 + aios init --all），你照常用 codex / claude / gemini，AIOS 在底下做四件事：

你说一句话
"重构认证模块"
→
AIOS 记忆
翻出上周的相关决策
→
rex 工序引擎
拆成一步一步的工单
→
AIOS 执行
单干 / 并行 / 长任务
→
验证证据
测试回执、审查记录
→
交付
经过验证的结果

对应到功能清单：

能力命令人话解释
项目记忆aios memo add / search、ContextDB给项目配一个"本地档案室"：重要的决策记下来，下次自动翻出来用。
任务路由aios plan auto-gate判断这句话是小问题（直接答）、小改动（加门禁）还是大活（先立计划），防止杀鸡用牛刀。
多 Agent 并行aios team 3:codex "..."把活拆给 3 个 AI 同时干，各管各的文件，最后汇总。
可恢复长任务aios harness run --objective ...让 AI 跑通宵大任务：每一步存档（检查点），断了可以接着跑，还在独立的 git worktree 里干，不弄脏你的工作区。
验证与安全aios doctor、privacy guard体检安装状态；敏感文件（密钥等）在分享给模型前先脱敏。
"你的数据保持本地"是认真的吗？ 是的。README 原话："你的数据保持本地。一切——记忆、日志、验证——都在你的机器上运行。什么都不离开。" 所有记忆都是你项目目录里的普通文件（.aios/ 文件夹），可以直接用文本编辑器打开、用 git 备份、不想要了直接删。唯一出网的流量是模型 API 本身（这跟你平时用 AI 客户端一样）。

1.3 rex-harness：那个"铁面无私的质检员"

rex-harness 解决的是上面第二、第三个毛病。它的核心循环用大白话讲就是：

第 1 步 · 看情况：收集"观察"（Observation），比如"测试挂了""用户要改行为"，推导出"事实"（Fact）。每条事实都必须附上来源证据，AI 拍脑袋的直觉不算数。

第 2 步 · 发一张工单：根据事实，从 13 种标准工序（需求澄清、设计、规划、测试设计、TDD、调试、最小实施、代码审查……）里挑正好一个，生成一张工单（Provider Command），告诉 AI："现在只做这一件事，做完要交这些材料。"

第 3 步 · 验收：AI 干完交回"证据"（Evidence）。rex 检查：证据类型对不对？引用是不是真的？测试回执的退出码是不是符合预期（红测试必须非零退出，绿测试必须零退出）？不合格就阻塞，绝不放行。

第 4 步 · 循环：验收通过，发下一张工单；所有工序完成，任务才算"完成"。"完成"这个词由 rex 定义，不由 AI 嘴上说。

一个防作弊的巧思 每张工单都带一个一次性令牌（commandToken）。AI 提交证据时必须带上当前令牌；证据被接受后令牌立刻换新，旧的作废。这样 AI 就不能用"上次任务的旧回复"来冒充本次的交付——类似银行转账的动态口令。

1.4 它俩怎么配合：总部与核心车间

把两个仓库放在一起看，分工非常清楚：

问题rex-harness（内核）AIOS（宿主）
活该怎么一步步干（工序）？✅ 它定照办，无权改
AI 说"做完了"，怎么验证？✅ 它验复用它的验收逻辑
谁来真正运行模型、跑命令？❌ 不管✅ 它调
跨会话记忆、交接文档？❌ 没有✅ ContextDB / memo
并行多 Agent、断点续跑？❌ 没有✅ team / harness
隐私脱敏、安装体检、审计？❌ 没有✅ doctor / privacy guard

物理上，rex-harness 整个仓库作为子模块放在 aios/rex-harness/ 里；AIOS 的安装脚本甚至会在子模块缺失时自动执行 git submodule update --init 把它拉下来。rex-harness 自己的 README 也明说："它可以单独辅助各类 AI Agent；接入 AIOS 后，再获得模型执行、ContextDB、Team、长任务恢复和安全治理等宿主增强。"

AIOS 架构篇：一共几层、每层是什么、怎么实现

先看运行时的 7 层，再深入你最关心的"数据分几层"。

2.1 运行时分层：自上而下 7 层

官方架构文档（docs-site/architecture.md）给出的分层与源码完全对得上。下面每一层都标注了实际实现文件：

① 客户端入口层把"项目指引 + 路由提示"写进各客户端的原生配置面：往 CLAUDE.md / AGENTS.md / GEMINI.md 里写标记注释，把技能（Skill）投影到各客户端的技能目录。scripts/lib/native/emitters/*.mjs（每个客户端一个 emitter）· client-sources/ · scripts/contextdb-shell.zsh
② 启动桥接层决定"包一层启动"还是"直接放行"，并在一次性运行里自动完成：建会话 → 记录用户输入 → 跑真正的 AI 客户端 → 记录回复 → 自动写检查点。scripts/contextdb-shell-bridge.mjs · scripts/ctx-agent.mjs → scripts/lib/ctx-agent-core/run.mjs
③ ContextDB 记忆层本地项目记忆库：会话、检查点、memo、上下文包的存储与检索（第四章详解）。mcp-server/src/contextdb/（TypeScript：core.ts / sqlite.ts / semantic.ts / hygiene.ts）+ 磁盘目录 .aios/context-db/
④ 工作流策略层给每个请求定风险等级：noop（无事）/ direct（直接答）/ guarded（小改动+门禁）/ planned（大活先立计划）/ blocked（信息不足）。纯函数实现，不猜语义。scripts/lib/planning/workflow-policy.mjs · auto-gate.mjs · cli.mjs
⑤ 运营调度层真正派活的层：team（多 Agent 并行）、harness（可恢复长任务）、orchestrate（分阶段 DAG）、HUD（状态仪表盘）。scripts/aios.mjs（入口仅 34 行）→ scripts/lib/cli/dispatch.mjs → lib/lifecycle/、lib/harness/
⑥ 浏览器运行时通过 CDP 协议驱动 Chrome 做"读→做→验证"的网页操作循环（旧 Playwright MCP 保留为兼容路径）。scripts/run-browser-use-mcp.sh · config/browser-profiles.json
⑦ RL 研究层隔离的多环境强化学习实验场（训练/评测脚本），官方明确说明它不属于生产路径，只是研究证据。scripts/lib/rl-core/ · rl-shell-v1/ · rl-mixed-v1/
第④层的实现哲学值得单独说 workflow-policy.mjs 源码里写了一段"北极星原则"注释：本模块绝不用关键词正则从自由文本里猜"用户想干嘛"，只认两类输入——显式协议前缀（比如 /plan:、/team: 这样的斜杠命令，以及中英文的确认词）和调用方显式声明的意图（explicitIntent）。语义判断交给 AI，记账和路由交给确定性代码。这个"模型管语义、代码管簿记"的原则贯穿整个 AIOS。

2.2 数据分层：你问的"哪几层数据"——答案在这里

AIOS 的所有状态都落在项目根目录的 .aios/ 下。它可以分成四大区、六个抽象层次：

.aios/ ← AIOS 状态根目录（可整目录备份/删除） ├── context-db/ ← 会话记忆区（ContextDB） │ ├── index.json L-1 源注册表：告诉客户端"这里有哪些记忆源可查" │ ├── sessions/<会话id>/ L0~L2 原始数据层（唯一的"事实源"） │ │ ├── meta.json 会话元信息：目标/标签/状态 │ │ ├── l0-summary.md L0 摘要层：这段会话干了啥（每次 checkpoint 重写） │ │ ├── l1-checkpoints.jsonl L1 检查点层：一条行=一次存档（进度/下一步/产物） │ │ ├── l2-events.jsonl L2 原始事件层：用户说了啥、AI 答了啥，逐条流水账 │ │ ├── state.json 游标：读到第几条事件/检查点了 │ │ ├── continuity.json + .md 连续性摘要：改过哪些文件、接下来干嘛 │ │ └── handoff.json 交接包：给"下一个接手的会话"看的 │ ├── index/ L-2 派生索引层（可以随时删掉重建的缓存） │ │ ├── sessions/events/checkpoints .jsonl 倒排索引行 │ │ └── context.db SQLite 库 + FTS5 全文索引（注释明说"可重建缓存"） │ └── exports/ L-3 导出层：人工挑选打包的上下文包（带 sha256 清单） ├── memo/ ← 持久决策记忆区（比会话更"长期"） │ ├── file/events.jsonl 默认后端：只追加的事件流（一行一条 memo） │ ├── split/ 可选后端：一条 memo 一个 JSON 文件 + pinned 置顶 │ ├── derived/ 检索用派生层（可重建） │ ├── dream/ 记忆生命周期：提案/治理/归档（老记忆"睡一觉"再决定去留） │ └── memory-recall-feedback.jsonl 反馈层：记录"哪条记忆真的被用过" ├── offload/ 大体积工具输出外置区（画布索引 + 节点引用） └── tasks/ workspace/ 任务与工作区状态 .rex-harness/ ← rex 侧的独立状态（在 rex 独立模式下使用） ├── workflows/ work-item 索引（sha256 文件名） ├── activations/ 完整工作流状态 JSON（规范状态） ├── evidence/ 只追加的 NDJSON 证据日志 └── receipts/ 命令执行回执（退出码 + 输出哈希）

把上面的物理结构抽象一下，AIOS 的数据一共是这六个逻辑层次：

层名字内容特点
L0摘要层l0-summary.md一屏读完"这段会话干了什么"，每次存档被重写
L1检查点层l1-checkpoints.jsonl结构化进度条：目标/状态/下一步/产物，长任务恢复靠它
L2原始事件层l2-events.jsonl逐条流水账，最完整也最大；检索的主要对象
L-1注册表层index.json（源注册表）只存"指针"：有哪些记忆源、多大（~1KB 级）、优先级，不复制内容
L-2索引层index/*.jsonl + SQLite FTS5纯派生缓存，删了可用 index:rebuild 从 L0-L2 全量重建
L-3导出层exports/*-context.md按 token 预算精选打包的上下文包，附 sha256 清单防篡改
这套分层最重要的设计原则 原始层（L0/L1/L2 + memo JSONL）是唯一事实源，一切索引都是可丢弃、可重建的缓存。SQLite 只做全文检索加速（FTS5 虚拟表），源码注释原话是 "SQLite sidecar is a rebuildable cache; canonical session files already persisted"。这意味着：记忆不怕索引损坏、不怕换工具——所有数据都是人类可读的 Markdown 和 JSONL。

2.3 每层怎么实现：三个有代表性的机制

机制一：写检查点 = 一次写七处（事务式簿记）

当一次会话到达存档点，core.ts 里的 writeCheckpoint() 会原子地完成一整套动作：

追加一条到 l1-checkpoints.jsonl
↓
重写 l0-summary.md（摘要刷新）
↓
重写 continuity.json / continuity-summary.md
↓
更新 meta.json 状态 + state.json 游标
↓
追加到 index/checkpoints.jsonl（索引层同步）
↓
SQLite + FTS5 upsert（检索缓存同步）

并发安全靠会话级文件锁（.session.lock，10 秒超时）。长任务（aios harness run）每轮迭代都会调这个检查点，所以断电、崩溃、Ctrl-C 之后都能从 L1 检查点续跑。

机制二：三种执行模式（team / orchestrate / harness）

模式适用实现要点
aios team
多 Agent 并行		 几个互不依赖的活 源码注释明说"team 命令最终复用 orchestrate"——它只是把"3 个 codex"翻译成 3 个本地派发参数。每个并行任务通过 phase-rex.mjs 绑定各自的 rex activation 和 ownedPathPrefixes（文件所有权），禁止两个 Agent 同时改同一个文件。实时并行需显式开启 LIVE_EXECUTION_ENV=1，默认是安全的 dry-run。
aios orchestrate
分阶段 DAG		 有依赖关系的多阶段工程 内置 4 种蓝图（feature / bugfix / refactor / security）× 4 种角色（planner / implementer / reviewer / security-reviewer），生成带 dependsOn 的任务图；4 种运行时（本地演练 / 真实子代理 / 群聊 / 仿真）可切换；跑之前先过质量门（quality gate + doctor）。
aios harness run
可恢复长任务		 一个明确的长期目标（如"今晚完成发布交接"） 三件套：① 每轮迭代写检查点到 ContextDB；② git worktree add --detach 在临时目录开独立工作区，不弄脏你的分支；③ 状态机 running / done / blocked / failed / backoff / human-gate / stopped——遇到需要人的决策就停在 human-gate，断线可 resume。结束时若有未合并改动或异常状态，worktree 会被保留供你检查。

机制三：init / doctor——装得上，更要查得出问题

aios init --all 按固定顺序做八件事：确保 rex 子模块就绪 → 用 which 探测你装了哪些客户端 → 建工作区（注册表、技能索引、常驻"工作区记忆会话"）→ 征求同意后装压缩工具链（RTK / Caveman / Headroom）→ 往 CLAUDE.md / AGENTS.md / GEMINI.md 写指针标记 → 写客户端钩子配置 → 迁移 MCP 配置 → 投影 rex 技能。aios doctor 则是 366 行的聚合体检：rex 子模块是否存在（硬性必需，缺了直接报错）、浏览器 MCP、ContextDB 技能、token 纪律、安全配置等，支持 --fix --dry-run 先演习再修复。

3

rex-harness 深挖：让 AI"交作业"的引擎

约 58 个源码文件的纯函数内核，每一处细节都指向同一个目标：AI 的自由行动必须收敛为"可验证的单步循环"。

3.1 领域模型：一条严格的数据链

Observation
观察：发生了什么（14 种）
→
Fact
事实：可追溯的结论（26 种）
→
Capability
能力：选正好一个（13 种）
→
Command
工单：当前唯一要做的事
→
Evidence
证据：类型化交付物

每一环的数据结构都在 src/domain/ 下，全部是冻结对象（Object.freeze），字段多一个少一个都直接抛异常：

概念定义文件关键字段与硬规则
Observation domain/observation-kinds.mjs 14 种枚举（如 test.regression-observed、change.behavior-requested）；只允许 {kind, evidenceRefs, changeRisk} 三个字段；风险维度（changeKind / blastRadius / externalEffect / reversibility / uncertainty）只有一种观察允许携带。
Fact domain/fact-kinds.mjs · facts.mjs 26 种枚举（如 explicit-intent、honest-red-candidate、execution-failed）；每条 Fact 必须带 evidenceRefs——源码注释明说：这是为了"避免使用无法追溯的模型直觉作为路由理由"。
Capability domain/capability-ids.mjs · capabilities/*/capability.mjs 13 个稳定 ID（需求澄清 / 设计 / 规划 / 测试设计 / TDD / 严格 TDD / 加固 / 根因调试 / 最小实施 / 执行 / 规范审查 / 专项审查 / 寻路）。每个能力自带：优先级、激活条件（activate(facts) 纯函数）和内部工序（recipe）。
Activation domain/activations.mjs 一次能力激活的完整状态：{stageIndex, stageId, completedStages[], evidence[]}。注释强调"只保存可恢复的语义状态"。
Command domain/commands.mjs 当前唯一工单：{provider, objective, expectedEvidence[]}——白纸黑字告诉 AI"交什么"。
Evidence domain/evidence.mjs {kind, refs[]}；每个引用必须带协议前缀（如 artifact:requirements、receipt:xxx）；同 kind 的引用可累积合并。

3.2 两层状态机：外层选工序，内层推进度

rex 有两个嵌套的状态机，这也是它架构文档里最核心的一节：

外层 · 软件工作流运行时（workflows/software-workflow-runtime.mjs）

决定"下一个该干哪道工序"。每完成一道工序，它基于更新后的事实集 + 已完成工序 + 证据重新选择下一个能力（而不是按写死的剧本走）。三个著名的阻塞规则：

  • 意图未知 → blocked: explicit-intent-unknown（不让 AI 猜任务）
  • 想审查但没有 diff 证据 → blocked: review-requires-diff
  • 想调试但没有可复现的失败 → blocked: debug-requires-reproducible-failure

选择算法是确定性的：过滤掉已完成和未启用的能力，按优先级降序 + ID 字典序取第一个。没有任何随机性、没有 LLM 调用。

内层 · 能力内部工序状态机（application/advance-activation.mjs）

以 TDD 为例，内部是经典三段（但每段都有独立的证据门）：

red 红阶段
先写失败测试
要求：失败测试已观察
+ 失败原因已记录
→
green 绿阶段
最小实现转绿
要求：通过测试已观察
+ 实现差异已记录
→
refactor 重构阶段
清理不改性
要求：重构检查已记录
+ 测试差异已复审

两层的衔接规则：内层没走完 → 外层保持 active，给当前阶段重发工单；内层走完 → 外层重新基于事实选下一道工序；测试可行性决策为 blocked → 触发 replan（重新规划）而不是硬闯。另有一条防重复的等价规则：TDD/严格TDD/加固完成即视为"测试设计"与"实施执行"已满足，避免同一片代码被实施两遍。

3.3 防造假机制：五层门禁，全部 fail-closed

这是 rex-harness 最精彩的部分。AI 提交的证据要过五道关，任何一道不过都是阻塞而非报错继续（fail-closed 哲学：宁可停下来等人，绝不带着问题往下走）：

#门禁实现（application/validate-command-evidence.mjs 等）
1种类白名单只能提交当前工单声明过的证据种类（expectedEvidence）。想交"计划外的证据"蒙混？直接拒绝。
2引用格式必须匹配协议前缀正则 /^[a-z][a-z0-9+.-]*:.+/iu，且命中 /artifact-or-command-ref|placeholder|真实存在|todo|tbd/iu 的占位词直接判无效——连中文占位词"真实存在"都被防了。
3执行回执关键证据必须附 receipt: 引用：红测试（failing-test-observed）的回执退出码必须非零，绿测试（passing-test-observed）必须为零。回执由 rex 亲自 spawn 命令捕获（rex-harness receipt -- <命令>），记录退出码、绝对工作目录、stdout/stderr 的 sha256，还要核对该命令与决策声明的场景命令逐项一致。
4一次性令牌每次成功写盘前给工单盖新 randomUUID() 令牌；提交证据必须带当前令牌，验收通过即换新，旧令牌重放立即被拒。被拒时保留旧令牌让调用方原身份重试——细节考虑得很周到。
5状态自愈为零所有写盘走"临时文件 + rename"原子替换；读盘时校验 schema 和命令契约；状态损坏不会猜测性修复，而是阻塞并要求人显式处理。证据日志（NDJSON）只追加、永不覆盖，审计可回放。

3.4 SKILL.md：rex 是怎么"指挥"AI 的

rex 不注入任何提示词黑盒，而是把行为规范写成客户端原生可发现的技能文档（skill-sources/）。编排入口 rex-workflow/SKILL.md 的第一步是一张真值表：

# rex-workflow 给 AI 的指令（节选意译）
收到 rex-harness 返回的紧凑对象后，按真值表行动：
  status=active   且 command 非空            → 只执行这张工单
  status=completed 且 command=null 且无缺失  → 停止，任务完成
  其他任何组合                            → 状态损坏：fail-closed。
                                            不执行残留 Provider、
                                            不声明完成、不猜测补造证据

几个代表性 Provider 技能的"诚实性条款"：

  • rex-tdd："语法错误、环境问题导致的失败不算合法的 RED"；"删测试、削弱断言来换 GREEN"被明令禁止；不得用实现反推测试。
  • rex-code-review：双轴独立审查（规范轴 + 规格轴，各 ≤400 字），每条发现必须带位置、证据、严重度；专项审查按风险域从 5 名内置评审专家（安全 / 正确性与数据 / API 兼容 / 性能与并发 / 前端可访问性）里按证据选恰好一名——"没有风险证据时拒绝角色表演"。
  • 评测集：每个技能目录带 evals/evals.json，不仅有标准问答，还有 pressures 压力场景（deadline 诱导、权威诱导、沉没成本诱导）——专门测试 AI 会不会在压力下作弊。

3.5 CLI 与安装投影：面向模型的"低带宽协议"

rex 的 CLI 默认只返回一个叫 rex.cli.workflow-command.v1 的紧凑对象——只有当前状态、工单、缺失证据清单和一次性令牌，完整历史留在磁盘里不进上下文（省 token 的设计）。需要诊断时加 --full。而 rex-harness init --client claude 会把技能投影到对应客户端目录（.claude/skills 等），安全机制相当完备：

  • 内容寻址：对投影目录做规范化 sha256，写入 .rex-projection.json 标记 + 投影历史；
  • 决策表：目标不存在→安装；内容相同→跳过；内容不同但在历史中→更新；否则→conflict 报错退出（绝不覆盖你的同名用户文件）；
  • 防呆：拒绝符号链接、拒绝路径逃逸、staged copy + 备份 + 失败回滚，连"上次安装中断的残留"都有专门恢复逻辑。
4

AI 本地记忆深挖（重点章节）

你特别问的"AI 本地化记忆"：AIOS 在这块下了最大的功夫，设计上有几个非常独特的点。

4.1 核心理念：拉取式（pull-based），不是灌注式

大多数"AI 记忆"产品的做法是把历史记录塞进每次对话（prompt 注入）。AIOS 明确反对这条路——AGENTS.md 里写着 "Runtime context is pull-based: do not inject session history"。它的模型是：

客户端启动
读到项目指引里的指针
→
index.json 注册表
"有哪些记忆源可查"
→
Agent 按需检索
只拉当前任务需要的
→
带着最少够用的上下文干活

为什么要这样？因为全量注入记忆的方案会随着历史增长而失控：上下文窗口被旧流水账占满，token 费用飙升，AI 反而更容易被噪音带偏。拉取式把"记什么"和"何时用"解耦了——记忆可以无限长，每次使用的成本恒定。

4.2 记忆的三条读取链路

链路适用客户端工作方式
① 钩子自动注入 Claude Code、Codex（支持 hook 的） 你每发一条消息，user-prompt-submit 钩子先跑统一搜索（unified-search.mjs），把命中的记忆以 ## AIOS RECALL 块注入本轮上下文。预算极克制：最多 6 条、总共 2000 字符、单条 320 字符。查询还有"梯子"：先用原句搜，搜不到就降级到内容词，再降级到 token 二元组——逐级放宽，保证不空手而归也不一次灌满。
② MCP 工具调用 Gemini、Hermes 等无 hook 的客户端 v5.9.0 新增 aios-memory MCP 服务器（stdio JSON-RPC），提供三个工具：memory_recall（检索）、memory_write（落 memo）、memory_checkpoint（存档）。配套一份"记忆触发契约"写进各客户端指引：新会话先 recall、说"继续"先 recall、验证出结论立刻 write、声称做完之前必须 checkpoint。
③ 显式 CLI / 技能指令 所有客户端的兜底 Agent 通过技能指令学会标准检索姿势：contextdb search 找事件 → timeline 看时序 → event:get 钻取单条；外置大输出则 canvas show 看任务图 → refs grep 窄搜 → refs read 只读需要的节点。

4.3 最独特的设计：记忆使用反馈闭环

这是我见过的比较少见的记忆设计 AIOS 不满足于"召回记忆"，它还追踪"召回的记忆到底有没有被用上"。流程是：钩子注入记忆时，同时要求 AI 在回复末尾附一个声明块 <!--memory: verified=yes, useful=<eventId>...-->；系统解析这个声明，只有 AI 明确声明"确实用过且有用"的记忆才记入 memory-recall-feedback.jsonl；下次检索时，被证实有用的记忆获得排序加权（feedback boost）。这相当于给记忆系统装了一个"实用性回流"机制——记忆不是越多越好，而是越被验证有用越靠前。

写入侧同样讲究"模型决策、代码执行"：memo 技能的原则是 "you decide, the harness executes"——什么值得记、什么该被新结论替代（supersede），由 AI 语义判断；文件锁、追加写、版本链、权限校验，全部由确定性代码完成。memo 还支持 scope 分级：project_shared（全客户端共享）和 agent_private（仅本 Agent 可见，且 30 天后自动隐藏但不删除——只隐不删，留了反悔余地）。

4.4 一个必须坦白的真相：没有任何向量检索

如果你以为"AI 记忆 = embedding + 向量数据库"，这里会颠覆认知 全仓库找不到任何 embedding 模型或向量库。源码注释直说了这一点："there is no vector backend yet, but documents intent for future sqlite-vec integration"。唯一的"语义"组件是一个可选开关（CONTEXTDB_SEMANTIC=1）下的 token 重排器：Jaccard 相似度 0.6 + 包含度 0.4 的词元重叠打分。

那检索靠什么？纯关键词/token 统计，但做得相当细（memo/storage/query.mjs）：

  • 分词：拉丁词按词切；中文用 ICU 的 Intl.Segmenter 分词，并加 CJK 二元组（bigram）兜底——处理"认证"vs"登录验证"这类部分匹配；
  • 打分：子串命中 +2/+1 分，token 覆盖率 ×4/×2，加反馈加权；命中率阈值按查询长度自适应（≤2 词需 100% 命中，≤6 词需 50%，更长 34%）；
  • 过滤链：时间有效性（被替代的旧记忆不出现）→ 可见性（private 记忆别人看不到）→ dream 归档过滤 → 预算裁剪。

为什么不用向量？源码里有一句原则性注释："语义判断是 LLM 的工作，绝不是手工维护的对照表"——检索层只负责把候选粗筛出来，"这两条记忆说的是不是一回事"这种语义理解交给已经读完候选的 AI 自己判断。这是一个明确的工程取舍：用零成本、零依赖、完全离线、结果可解释的词法检索，换取 embedding 模型的部署成本和不可解释性。代价是：换一种说法、跨语言改述的同义记忆可能漏召回——这是它未来明确预留 sqlite-vec 的原因。

4.5 记忆的"压缩"与"外置"：token 预算的艺术

当确实需要导出一段历史时（context pack），AIOS 的选材逻辑是个三层漏斗：

组装候选：L0 摘要 + 最新检查点 + 连续性摘要 + 外置画布 + 过滤去重后的事件
↓
smart 召回策略：最近 50~180 条的池子里，一半保最新，另一半按"与目标+检查点的 token 重叠度"打分挑选（72 小时半衰期加权——越久远的记忆权重越低）
↓
token 策略：先无损压缩文本 → 不够就按优先级丢事件 → 最后逐条截断；全程统计"压缩了多少/丢了多少/截断了多少"写进导出报告

配套的还有一套五层 token 纪律体系（决策门 Ponytail → shell 输出过滤 RTK → 简洁风格 Caveman → 显式压缩 MCP Headroom → ContextDB 按需召回替代全量注入），以及一个很实用的 offload 机制：超过约 2KB 的工具输出（比如一次巨大的网页抓取）不进上下文，落到 .aios/offload/，上下文里只留一个 Mermaid 任务画布和节点 ID，AI 需要时用 refs grep 窄搜、refs read 精读——"省下来的是未来的上下文空间"。

4.6 隐私与记忆的交界：在"读出端"设卡

privacy guard 的配置在 ~/.rexcil/privacy-guard.json，检测两类风险：敏感路径（glob 规则）和敏感内容（私钥、sk-、AKIA、ghp_、JWT 等特征）。脱敏支持三种模式：regex（纯正则）、ollama（本地小模型判断，失败自动回退正则）、hybrid（混合）。关键的设计决策是：写入记忆时不强制脱敏（保持原始层 append-only 的完整性），而是在读出/分享路径上拦截——skill 里明确要求"节点可能含密钥时，先过 aios privacy read 再分享"，子代理的执行上下文也会先过脱敏器。这个取舍和它"原始层不可篡改"的原则是自洽的。

关联性评价与整体解读

把两仓库放回一起，给出我的整体判断。

5.1 关系全景：一个刻意做薄的边界

AIOS 宿主
记忆 · 执行 · 安全 · 协作
⇄
唯一适配边界
rex-harness-adapter.mjs
只调 JS API，不解析 CLI
⇄
rex-harness 内核
Fact→Capability→Evidence 状态机

集成方式有四个值得记录的事实：

  • 物理形态：rex-harness 是 AIOS 仓库唯一的 git submodule（.gitmodules 注明用 HTTPS URL 是为了 CI 无 SSH key 也能拉取）；release 安装包已内置固定版本，用户不需要装第二个 npm 包。
  • 代码边界：AIOS 侧的 scripts/lib/workflows/rex-harness-adapter.mjs 文件头自述"AIOS 与 rex-harness 的唯一适配边界"，直接相对路径 import rex 的 src/index.mjs，调用 startSoftwareWorkflow / advanceSoftwareWorkflow / evaluateSoftwareRequest 等——不走 CLI、不解析 stdout，因为 JS API 保留完整 Workflow 对象，而 CLI 紧凑协议是留给"外部 Agent 直连"场景的。
  • 反向声明：rex 侧的 src/aios/manifest.mjs 只输出可序列化的声明式清单（剥离函数闭包），注释写道"宿主跨越此边界消费的是声明，而不是可执行闭包"——两边都在刻意防止对方伸手指进来。
  • 纪律约束：rex 的架构文档用一张"所有权表"明确禁止宿主做的事：AIOS 不得重选 Capability、不得重写证据契约、不得重排阶段、不得绕过状态机；适配层甚至不能替换 Provider。"软件工作流的唯一运行时事实源是 software-workflow-runtime.mjs" 这句话在两个仓库里反复出现。

5.2 设计哲学评价：四个我认为最值得学习的决策

① "模型管语义，代码管簿记"——贯穿始终的分工律

workflow-policy 拒绝从自然语言猜意图、rex 的 Capability 选择是纯函数查表、memo 的写入由模型决策而持久化由代码执行。凡是需要"理解"的地方交给模型，凡是需要"可靠"的地方交给确定性代码，且两者之间的接口是显式声明而不是猜测。这直接回答了"AI 系统怎么做到可测试"：因为核心状态机不依赖模型，npm test 就能把 58 个内核文件全部测透（rex 的测试甚至覆盖了"token 重放被拒""损坏状态 fail-closed"这类对抗场景）。

② "证据优先于结果"——把信任问题变成工程问题

AI 最大的可靠性问题不是"不会做"，而是"说做了其实没做"。rex 的回应是不接受任何口头汇报：测试回执必须由 rex 亲自 spawn 并核对退出码（红=非零、绿=零）、stdout/stderr 存哈希防篡改、命令与声明的场景逐项比对、一次性令牌防重放。这本质上是把"信任"从人际承诺降级为密码学级别的簿记。配套的 fail-closed 哲学（损坏不修复、只阻塞；宁可停机也不带病运行）在两个仓库里高度一致。

③ "文件优先，数据库只是缓存"——本地优先的彻底执行

所有状态都是人类可读的 Markdown/JSONL：会话是 l2-events.jsonl，决策是 memo/file/events.jsonl，证据是 NDJSON 日志。SQLite + FTS5 只是可重建的加速层。好处是三重的：数据可随时用 git 备份/同步、格式永不锁定（换工具迁移零成本）、调试时直接 cat。配合"原始层只追加、派生层可丢弃"的分层，这套系统的数据健壮性远超一般脚本项目。

④ "拉取式记忆 + 使用反馈"——对记忆系统的清醒认知

大多数记忆产品在堆"存得多"，AIOS 在抠"用得准"：6 条/2000 字符的注入预算、查询降级梯子、offload 外置、smart 召回的 72 小时半衰期，以及那个少见的声明式反馈闭环（只有被 AI 证实"真的用过"的记忆才获得排序加权）。这套设计承认了一个行业普遍回避的事实：记忆系统的瓶颈不在存储，而在每次调用的注意力预算。

5.3 局限与风险：同样值得知道的另一面

局限说明
词法检索的天花板 没有 embedding 意味着"换了说法的记忆"可能搜不到（比如当初记的是"登录鉴权"，你问"认证"能否命中取决于 bigram 重叠度）。仓库已预留 sqlite-vec 意图，但今天它就是关键词级的。好在"语义判断交给 LLM"的兜底 + 查询降级梯子缓解了大半。
显式协议的上手成本 "绝不猜语义"意味着输入端必须守协议：意图要显式声明、确认要走确认词。用户随手一句模糊的话可能得到 blocked: explicit-intent-unknown。对新手有摩擦，换来的是行为的可预测性——这是取舍，不是缺陷，但需要适应。
规模与复杂度 AIOS 的 scripts/ 有约 1080 个文件、15 万行，虽然"薄壳入口 + 门面 + 子域拆分"的组织相当整齐，但理解全貌的成本不低；文档与代码偶有漂移（例如 rex README 说 .rex-harness/ 有三个子目录，代码实际是四个——receipts/ 是后加的）。
客户端能力不均匀 hook 自动注入只在部分客户端可用（codex/opencode/hermes/grok 靠桥接或 MCP 兜底），不同客户端的体验深度不同，官方也只能让你"以 doctor 的本机结果为准"。
submodule 的双刃剑 固定版本保证了可复现，但普通 clone（不带 --recurse-submodules）会缺失内核——好在这点被 init/doctor 的自动拉取和明确报错兜住了。

5.4 总评

一句话总评 这是一对"把 AI 当成一个能力很强但需要被制度约束的员工"来设计的系统：rex-harness 证明了 AI 工作流的核心可以做成纯函数状态机 + 类型化证据门（可测试、可审计、防作弊），AIOS 证明了在它之上可以叠出完整的本地优先操作系统（记忆、并行、恢复、隐私），而两者用"唯一适配边界 + 所有权纪律"维持了教科书级的关注点分离。如果你想研究"AI Agent 的可靠性工程"，rex 的防造假五门禁和 AIOS 的拉取式记忆反馈闭环，是我认为最值得逐行精读的两处。

用官方架构文档里的 "Graph Engine" 视角收个尾，两个仓库各自的角色一目了然：
