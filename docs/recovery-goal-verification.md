## 目标与范围

在当前 jt-harness 项目安装 Flow，用记忆异常恢复作为真实长任务，验证有序阶段、持久检查点、中断恢复和 Codex Goal 自动续轮。独立安装交付不在本次范围内，没有清空历史任务。后续用户明确要求改用 `deepseek-official / deepseek-flash` 并继续目标；仅改变 Provider/model，生成参数仍使用 Provider 默认值。

Flow 任务为 `d4454ab7-8e68-4bef-875d-3901781fe69b`。最初回补对象为 13 个 failed、4 个 partial 和修正产生的后续批次。用户指定官方模型继续后，将同一项目在此次模型切换前受断网影响的另外 17 个失败批次一起恢复，包含最初排队和测试期间接收的材料。切换后的新会话继续走正常队列，不持续扩大本轮回补边界。

## 已交付行为

- `memo retry` 从已有提炼检查点继续；原错误追加到 `jobs.failure_history`，不再因清除当前 error 而消失。
- Embedding 网络异常现在明确标出请求阶段并保留底层连接原因，避免将不明来源的 `fetch failed` 误判为 DSH 提炼问题。操作者主动中断仍保留中断语义，公开错误输出继续脱敏。
- `memo recover <id>` 展示原 issue、修正回执、后续任务和未解决数量；`memo recover <id> corrections.json` 按原路径接收显式修正或说明不采纳原因。
- 修正提炼条目另建后续批次，保留原接收时间和执行配置，跳过再次提炼。原有效正文、向量和回执保持不变。
- 修正关系复用原条目与向量，沿用事务、范围、证据和时效规则。已失效的新条目不能被旧修正重新启用。
- 原模型输出和诊断保留。相同修正幂等；冲突修正拒绝覆盖；一份修正请求中途出错会整份回滚。
- 实测发现 JSONB 改变对象字段顺序，会使字符串比较错误地放过重复事实或拒绝同一修正。已有事实使用标准库结构比较，恢复回执使用 PostgreSQL JSONB 等值比较；真实 PG 回归覆盖两种情况。

恢复入口由主 Agent 或调用者核对来源后提供修正。没有另起一个修复模型，也没有将 `partial` 重新提炼成整批新数据。补录条目的旧记忆比较仍由现有 DSH 路径执行。

数据库从 v5 增量升级至 v6，增加恢复回执与错误历史。旧代码不能直接连接 v6；代码回退应同时考虑数据库版本。升级前数据库备份保存在本机 `.jth/backups/memo-before-recovery-v6-1789725382074.dump`，大小 4,596,827 字节，权限 0600。

## 阶段与 Goal 的分工

本次使用同一个原生 Codex Goal，Flow 保存四个步骤：安装与基线、实现与隔离验证、真实回补与恢复演练、最终验收与报告。

`phase` 表示讨论、执行、验收、完成；`steps` 表示具体工作阶段。步骤只能按顺序完成，必须记录结果证据；追加步骤使旧验收失效。步骤全完成仍须通过总目标验收。

原生 Goal 工具由主 Agent 调用，不由 jth 通过私有 App API 驱动。Skill 要求用户明确授权且宿主工具可用时才创建 Goal。恢复时读取 `get_goal` 与 `flow context`；阶段完成不关闭总 Goal，全部验收并 `flow finish` 后才调用 `update_goal`。

## 执行故障与恢复

33 项诊断均按原来源处理：修正消息 ID 的误抄、工具 JSON 中引文与时间证据的转义形式；跨范围关系或缺少合格端点的关系记录不采纳原因。后者只放弃不适用的关联，两端事实、已有修订证据和原模型输出继续保留。

本轮第一次重试 13 个旧 failed：3 个 complete，1 个转 partial 后已修复；另外 9 个发生执行失败，其中 7 个为 Embedding `fetch failed`，另外两个为 DSH 输出长度结束和超时。Embedding 后续实际探测返回 1,024 维，耗时 324 ms。连通恢复后，对这 9 个任务进行了第二次定向重试，执行配置没有改变。

随后最小 DSH 请求也返回 `Connection error.`，说明当前障碍并非只有大批次比较。读取现有 Provider 的地址进行无凭据连通检测：域名解析为私网地址，443 连接超时，错误为 `UND_ERR_CONNECT_TIMEOUT`。已请求用户恢复公司网络或 VPN，未切换 Provider 或模型。修正条目的后续批次也在 DSH 比较阶段遇到同一连接问题，其已保存正文保留。

内网阻塞连续三轮确认后，原生 Goal 曾标记 blocked；没有把 queued/running 当作成功。用户随后明确要求通过 jth 切到官方模型并继续，同一个 Flow 任务保持原目标、前两步和验收条件，新增约束明确覆盖先前冻结 Provider/model 的要求。

实际执行 `jth memo model --provider deepseek-official --model deepseek-flash` 后，最小 DSH 请求 3,417 ms 成功。选择命令不隐式修改旧队列，因此增加了 `memo retry <id> --provider <id> --model <id>`：校验选择后显式覆盖失败任务的 Provider/model，将原执行快照保留到 `failure_history[].agent`。来源、已存提炼和向量空间不变，没有添加 effort 或 token 上限覆盖。

消息 ID 修正的后续批次已在官方模型完成关系比较，只新增并嵌入该条记忆，默认检索可找到，父批次未解决数量归零。曾返回 `Response incomplete: length` 的原批次也已在相同提炼检查点上完成。全部五个补录任务均已结束，没有 publication_notes 或待处理诊断；其中一个只补录修订证据，合法地产生零条新记忆。
