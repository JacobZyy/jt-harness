# 任务拆分调整与实测（2026-09-24）

## 问题与依据

旧 `planningTemplate()` 虽要求按结果拆分，却同时返回按意图排列的 `focus` 阶段列表；部分意图包含“收集证据、修复、验证”等流程动作。`docs/flow-control.md` 又要求 planned 计划末尾安排“验收本次交付”。Codex 适配器把 Agent 写出的每个 `outcome` 直接映射为原生计划步骤，所以这些文本容易被模仿为顶层任务。结构校验只检查字段和依赖图，无法判断任务是否真的对应交付结果。

历史讨论确定的职责是：Agent 根据用户目标细化工作项，JTH 只给出轻量模板，Codex 原生计划记录进度。AIOS 的 `scripts/lib/planning/schema.mjs` 也先生成阶段骨架，再要求 Agent 细化；阶段骨架不适合作为最终原生计划。参考 [Anthropic 的 agent 设计指南](https://www.anthropic.com/engineering/building-effective-agents)、[CodePlan](https://arxiv.org/abs/2309.12499) 和 [ADaPT](https://arxiv.org/abs/2311.05772)，本次采用按实际问题分解、按证据更新的轻量做法，不增加第二套任务系统或模型评审。

## 对照方法

使用 `codex exec --ephemeral --ignore-user-config --skip-git-repo-check -s read-only -m gpt-6-sol`。每组向同一模型提供同一任务场景、相同 `goal/tasks` JSON 输出结构，仅切换模板：旧版的 `focus/guidance/verification` 与候选版的交付结果边界。人工逐项检查：顶层 `outcome` 是否代表用户目标的一部分；调研、编码、测试、回归或整体复核若不是用户明确要求的独立产物，是否被单列；依赖是否有实际先后关系。一个场景各运行一次，结果如下。

| 场景 | 旧模板 | 候选模板 |
| --- | --- | --- |
| 订单后台批量取消，逐笔结果，保留单笔行为 | 2 项：后端批量 API、前端选择与结果展示；通过 | 同样 2 项；通过 |
| 安全清理测试记忆、迁移凭据、重新接入 JTH | 3 项，其中“完成数据与接入状态的收口核验”仅是过程；未通过 | 4 项：可恢复快照、测试记忆清理、全局凭据、仓库接入；通过 |
| CSV 引号或换行损坏，根因未知，保留编码与列序 | 2 项：可验证根因、正确导出；通过 | 同样 2 项；通过 |
| 严格模式下只改设置页一个按钮文案 | 1 项，检查并入交付；通过 | 同样 1 项；通过 |

候选模板删去 `focus` 阶段列表，明确每个 `outcome` 是可独立验收的用户目标部分；准备和检查写入该项的 `doneWhen/verifyWith`。用户明确要求的研究报告、诊断结果或验收报告仍可单列。根因未知时允许先产出可验证诊断，再按证据细化。任务数量不固定。

另用候选模板检查三个边界：明确要求技术选型报告时，模型拆为项目约束、方案对比和推荐结论三个报告组成部分；只要求安装验证和报告时，拆为 Skill、CLI、Hook 的独立结果及最终报告；明确要求四项优惠券能力时，按创建、发放、核销、统计拆成四项。三组均未退化为通用流程阶段。

## 发行包验证

候选版 `pnpm build`、顺序执行的 `pnpm typecheck`、`pnpm test` 通过；离线测试 59 通过、26 跳过。`pnpm bundle` 生成 0.3.6 包，`npm pack` 后安装到独立临时目录。安装包的 `jth --version` 输出 `0.3.6`；`jth flow policy` 返回新模板、无 `focus`；从安装包执行 `jth flow install` 后，项目 Skill 链接及 `references/workflow-policy.md`、`references/acceptance.md` 均可读取。以上测试使用临时目录和占位配置，不连接真实数据库或调用 Embedding。

真实模型再从这个临时项目读取已安装 Skill，并以安装包内 CLI 的绝对路径调用 `jth flow policy`。输出为“测试记忆安全清理”“全局凭据迁移”“仓库重新接入”三项，没有独立测试或收口任务。模型把重新接入同时依赖清理和迁移；迁移依赖明确，清理依赖在没有项目证据时可能过强。模板只能提醒填写真实依赖，不能仅靠文字确保每次依赖判断正确。

模型样本规模有限，不能证明所有模型与任务都稳定产出优质计划。此次修复去掉明确的误导源，并保留原生计划与可复核证据；遇到新的拆分失败案例，应追加具体回归场景，再调整模板。
